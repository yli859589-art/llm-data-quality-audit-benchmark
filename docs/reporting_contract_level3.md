# Level 3 Reporting Contract

This document defines result labels and reporting rules for the Level 3 upgrade
path. It does not mark the project as Level 3 complete.

Canonical project status is maintained in `docs/PROJECT_STATUS.md`. Lowercase
status aliases should not be introduced unless they explicitly redirect to that
file.

## Core Status Labels

- `planned_protocol`: designed but not implemented or run.
- `implemented_but_not_run`: code exists, but no verified registered run exists.
- `run_and_verified`: registered run exists and artifacts pass checks.
- `failed_or_negative_result`: run completed or failed in a way that weakens the
  method claim; must be preserved.
- `unsupported_claim`: wording that is not backed by artifacts.
- `completed_evidence`: result has script, registry row, artifact, and check
  support.

## Main Results

`artifacts/tables/main_results.csv` and `artifacts/stats/main_results.csv` are
main-result artifacts. They can include only completed, traceable, non-fallback
training results that pass the configured purity checks.

Rules:

- main results cannot be hand-written;
- README summaries should reference generated artifacts instead of hand-writing
  experiment numbers;
- every main-result row must trace to a run registry record;
- fallback data cannot enter main results;
- smoke rows cannot enter main claims;
- failed rows cannot be deleted to make a method look effective;
- future protocols cannot be reported as completed experiments.

## Smoke Results

Smoke results are for engineering confidence and fast local checks. They may be
used to show that code paths execute. They cannot be used as main method
evidence.

Required label: `smoke_result`.

Forbidden promotion: a smoke result must not be described as a completed main
benchmark.

## Cross-Dataset Sample Results

Cross-dataset sample results include bounded real streaming-sample runs such as
current OpenWebText and C4 English samples.

Required label: `streaming_sample` or another explicit bounded-scope label.

Allowed claim: the project has bounded streaming-sample audit evidence.

Forbidden claim: full OpenWebText or full C4 completion unless the complete
upstream dataset was actually processed and recorded.

## Full Level 3 Results

A full Level 3 result must satisfy all of the following:

- data scope is verified;
- tokenizer identity is recorded;
- model scale and checkpoint identity are recorded;
- baseline/filter output manifest exists;
- multi-seed or justified seed protocol exists;
- training logs and loss curves exist;
- evaluation metrics are generated by scripts;
- result rows trace to the registry;
- claim hygiene passes;
- negative and failed runs are preserved.

Until these criteria are met, the repository remains an upgrade candidate.

## Planned Protocol

A planned protocol is not evidence. It may be written in docs and configs, but
must be labeled as planned.

Examples:

- URD-Selector design before registered runs;
- BPE mainline plan before verified training;
- downstream evaluation plan before completed downstream runs.

## Implemented but Not Run

Implemented code without verified runs can be described as infrastructure, not as
evidence. It must not change method status.

## Run and Verified

A run is verified only when:

- it appears in the run registry;
- required artifacts exist;
- purity and no-fallback rules pass;
- the interpretation is consistent with the claim boundary.

## Failed or Negative Result

Failed and negative results are evidence. They should be retained with clear
labels and failure reasons. They must not be removed to make a method appear
stronger.

## Unsupported Claim

An unsupported claim is any wording that describes planned or unverified work as
completed. Unsupported claims should be blocked by claim hygiene or manually
removed before release.
